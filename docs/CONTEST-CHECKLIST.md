# 参赛要求核对与部署阶段

核验日期：2026-10-16。官方来源：https://web3.okx.com/zh-hans/xlayer/build-x-series （TapeOut Accelerate，页面“参赛要求”“常见问题”“活动条款”）。规则如更新，应重新核对。

## 官方要求与当前差距

| 官方要求（概述） | SnapVault 的执行与证据 |
| --- | --- |
| 围绕 TapeOut 开发，实际使用 X Layer 上的 TapeOut 电路、合约或数据；提供相应地址 | 主要生态接入为真实 X Layer SiteRegistry 前端及网站容器，TapeSend 可选；当前仍是 localhost，未满足正式上线证据要求 |
| 应用类提供访问链接，说明实际使用的生态功能 | 当前 localhost 仅开发链接；正式提交前补可访问链接和生态地址/回执 |
| 已有项目说明活动期间新增开发 | 保留原前端，新增创作者广场、聊天付费图片、交付适配与测试；需以代码差异、演示和开发记录说明 |
| 项目说明覆盖产品、用户、触达、商业模式、付费与留存理由 | 现有 MVP 文档覆盖方向，正式提交前需结合最终实现核对 |
| 如使用电路类作品，提交相关处理器与电路信息 | 实际接入 TapeOut 身份/容器时记录其地址和 ID，当前未准备用户真实容器 |
| 按期提交说明和相关地址/链接 | 仍未提交；不由开发验证自动触发报名或接受活动条款 |

FAQ 允许界面等功能在电路外运行，也允许使用现有处理器和工具。因此“所有前端必须上链”“必须自建处理器”“所有业务合约必须归容器所有”不是本次页面明确列出的硬性条件；不能将自行设计的方案冒充官方要求。用户已明确要求正式前端必须真实运行在 X Layer DeWEB。它是当前方案的主要生态接入；TapeSend 可选，普通用户不用开容器。

**测试网部署与付款是工程验证，不足以独立满足 TapeOut 生态要求。** 最终业务合约、付款和订单仍按用户要求以 X Layer 主网为目标，真实主网花费必须另行由用户钱包确认。

## 当前钱包推进顺序

`payment-test.html` 是独立测试币演练，不出售内容，不调用 TapeSend。不会绕过 SnapVaultCheckout 的交付检查。`SnapVaultPaymentProbe` 构造时限制 chainId 为 1952 或本地 31337；不能部署到主网 196。

1. A 部署演练合约；构造函数自动建立无内容测试条目。
2. B 向该合约支付固定 0.00001 测试 OKB。
3. A 提回记账收入。此次创作者地址与平台费地址同为 A，因此同址余额合并；Purchase 事件仍明确记录 10% 费额。
4. 保存公开链上部署/付款/提现回执，分别记录与 TapeSend 交付无关的验证结论。

每次交易由用户在钱包确认。状态与部署证明保存在 Git 忽略的 `config/payment-test.local.json`，登记部署前由服务只读验证 chainId、发送方、完整创建字节码和构造参数，不接受任意地址冒充。

TapeSend 的官方测试网依赖缺口见 TESTNET-HANDOFF.md；解锁正式购买前必须解决，不以测试币付款演练代替。

只读链上查询、gas 估算通过同源 `/api/testnet-rpc` 转发到固定官方测试网 RPC；接口只允许读取和模拟，明确拒绝签名及广播。真正交易仅由钱包的 `eth_sendTransaction` 请求发起并等待用户确认。

## 最新规则确认：免容器普通用户 + 可选 TapeSend

2026-10-16 再核对中英文页面，英文 How to participate 第一条明确允许 run on X Layer DeWEB；Judging Criteria 明确不限定必须使用特定生态项目。前端真实上传 X Layer SiteRegistry、归网站电路容器并通过 DeWEB 访问，会实际使用 TapeOut 合约/链上数据，兼顾 FAQ 要求。普通用户不拥有容器、默认通过站内订单核验交付，不是规则禁止项。此为依据公开文本的技术路线判断，不是主办方资格审批。

提交时仍需访问链接、实际网站/电路/容器/付款合约地址、活动期间新增说明、用户与收入模式、可用完整流程；不能以仅普通 HTTPS 页面、空壳重定向或本地 fixture 代替 DeWEB。最新范围与预算见 MVP-PLAN.md。
