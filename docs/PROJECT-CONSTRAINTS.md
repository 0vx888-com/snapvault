# SnapVault 项目约束

> 2026-10-18 最新决定优先：TapeSend 必须作为正式交付方式接入生产 WalletService；有可用容器/公钥的买家优先 purchaseDelivered，无容器明确提示普通交付。C 和 operator 使用不同的新钱包，owner/treasury 用用户自己的主网钱包。上线前加固与顺序以 DEPLOYMENT.md 为准；以下旧阶段“可选”的说法已失效。主网付费和钱包签名仍需用户到时确认。

记录日期：2026-10-16；2026-10-17 补充长期项目与实施状态。来源：用户在本聊天中的明确要求。后续实现、部署和前端优化均应遵守。

## 已确定的项目方向

- 链上 Snapchat + OnlyFans + 创作者广场。
- 基于现有前端增量开发、优化，不推倒重做。
- 保留私聊、群聊、用户自设阅后即焚，并完善聊天内付费图片、创作者主页和广场发现。
- 前端后续仍需优化：统一广场与聊天的使用流程、改善移动端、理顺钱包和交付状态。用户此时要求记录后续事项，未要求立即启动一轮重设计。

## 长期项目优先级（2026-10-17）

- 用户明确要长期经营，同时尽快发布；先接好前后端、完整测试后上线，不以纯前端演示冒充可运营产品。
- 普通钱包登录、免费文字/发图/图文聊天、免容器付费图片交付为当前核心范围；保留可自设阅后即焚。
- IPFS 是可替换的内容存储方案，不是每项功能的强制条件；正式前端上 DeWEB 的要求保持。
- 新增实现与边界见 LONG-TERM-IMPLEMENTATION.md。当前完成本地闭环与静态跨域验收，未完成公开托管或新合约公共测试网部署，未花真钱。

## 早期阶段记录（已被顶部最新决定覆盖）

- 普通用户与创作者使用基本产品不要求自有容器；普通订单用钱包身份、链上订单与站内加密密钥交付。
- TapeSend 为用户主动选择的附加交付/收信能力，容器及开通成本仅属于这条可选通路。
- 当前方案与成本真源为 MVP-PLAN.md；普通交付与双通路合约已新增本地实现，公开测试网与主网部署仍待验证；不能把本地验证说成生产已上线。

## 参赛与部署约束

- 最终参赛版本的业务合约、付款和订单部署/运行在 X Layer 主网（chainId 196）。当前先在 X Layer 测试网（1952）验证。
- 用户最新明确要求：正式前端必须上传 X Layer 的 DeWEB 网站仓库，并通过 DeWEB 打开；普通 HTTPS 托管只可作为开发或辅助入口，不能替代此前端交付要求。
- 后续开发应以满足赛事官方规则为约束，不擅自迁移到其他链或用独立中心化产品替代参赛方案。
- “部署在 X Layer”本身不足以证明满足全部赛事要求。前端 DeWEB 托管、合约容器归属、链下/IPFS 内容存储是否符合要求，仍须以官方原文核验；本文件不把这些待核验条件写成已确认赛事规则。
- 正式参赛前应保存赛事官方规则来源并逐条记录满足情况，避免对外声称已符合尚未确认的规则。
- 真实主网部署和付费动作需到时由用户在钱包确认，当前测试授权不等于已授权主网花费。

## 交付真实性

- 本地模拟、官方源码本地测试、公共测试网上链、主网部署，必须分别标明。
- 不把本地测试容器、网关或投递测试当作官方 TapeOut 生态端到端验证。
- 当前公共测试网 TapeSend 仍有依赖缺口，见 TESTNET-HANDOFF.md。普通与 TapeSend 两条通路分别检查交付就绪，任一通路未就绪则禁止该通路收款；不能以禁用 TapeSend 绕过普通交付验证。
- 不承诺防截图、收回已交付密钥或彻底删除已传播内容。
