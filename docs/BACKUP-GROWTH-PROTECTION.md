## 实现

- 新运行备份使用明确指定的 generation（例如 `g-bounded-v1`），本地写入 `BACKUP_DIR/generations/g-bounded-v1/`，S3 写入 `snapvault/196:<vault>/generations/g-bounded-v1/`。原根目录、其他 generation、旧 latest、B0/B1 和独立查看账本都不属于新轮替范围。
- 默认只保留新范围内最近 12 份快照；远端另有一份完整加密 latest。不会清理旧前缀来腾空间。
- 使用备份密钥 HMAC 的输入摘要和已认证收据去重。忽略随机重新加密及纯订单扫描 cursor/anchor；资料、订单记录、退款、发送状态、预算、查看状态和未读正文均参与判断。重启后验证收据和快照，未变更不再写整份备份。
- 去重仍 HEAD 验证远端 latest 的大小和 SHA-256 元数据；缺失、变化或无法读取时失败关闭，不假装有有效远端备份。独立查看账本继续验证和同步。
- 上传部分失败时重用同一加密文件及名称；变化中的数据失败重试也只在新范围内有限轮替。S3 在 PUT 前为新文件预留保留槽，删除失败就不继续新增对象。列表支持分页。
- 磁盘余量不足保留旧文件，拒绝新增备份；备份验证失败阻断新报价和交付广播。
- 主网开启 worker 时必须有明确 generation 且修剪未暂停；不允许不指定隔离范围就开启主网修剪。本地和 S3 的 generation 必须相同。

## 兼容与恢复

`backupPolicyVersion:1` 明确版本化扫描进度摘要规则。旧状态先按原规则验证独立账本，再升级，原文件/备份在生产升级前另行保留；测试验证了升级、重启和新快照恢复。

纯扫描进度不再持续追加业务摘要。真实订单与发送状态仍受保护；恢复的旧扫描游标会重读日志。已消费/已结束查看仍由当前独立账本阻止复活。不得将独立账本回滚到旧水位。

新 latest 在新 generation 下，后续人工恢复/只读巡检必须选新路径，不能继续把旧根 latest 当作最新。`backup-state.mjs restore` 仍从明确下载的备份文件恢复，要求当前可信账本水位，拒绝覆盖已有目录。

升级后的状态不得配旧业务摘要算法镜像直接启动。回滚方式为本次支持新格式的后端镜像关闭 worker、必要时进入维护，保留当前数据/账本，不恢复旧数据覆盖新数据。原旧快照仍保留，但若遗漏后续业务写入会被拒绝恢复，这是防止丢数据的保护。

## 获准后的恢复步骤（本次未执行）

1. 复核当时费用、磁盘余量、当前数据/账本指纹与新 scope 未使用；保留当前及原数据、旧备份、B0/B1，不做清理。
2. 用户批准后仅部署后端。在维护中准备 `SNAPVAULT_BACKUP_GENERATION=g-bounded-v1`，`SNAPVAULT_BACKUP_PRUNING_PAUSED=false`，`SNAPVAULT_DELIVERY_WORKER_ENABLED=false`，维持迁移/初始化权限关闭。
3. 经授权退出维护启动新后端，验证新范围首份备份、远端 HEAD、旧订单/聊天/查看账本；有错误恢复维护，不开启付款。
4. 再只读核对 C、官方 Hub、nonce 和待发队列；出现未知任务或待确认交易先停。已经 sent 的旧任务跳过，不重复签名或发送。
5. 用户确认自动交付预算后才启用 worker/新付款报价。只做配置和路由就绪验收，不重新购买、发 TapeSend 或上传网站。任何额外付款另行报价。
